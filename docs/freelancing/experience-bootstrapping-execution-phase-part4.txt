SECTION 1: TESTING STRATEGY FOR PROJECT 1
================================================================================

1.1: TESTING LEVELS (SMOKE, FUNCTIONAL, RAG-SPECIFIC)
-----------------------------------------------------

For this project, you’ll think about testing in three practical layers:

LAYER 1 – SMOKE TESTS (DOES IT RUN?)
• Purpose: Quickly verify that:
  - The app starts.
  - The main endpoints respond.
  - The chat UI loads and can send at least one message.
• When:
  - After new deployments (staging or prod).
  - After major refactors.

LAYER 2 – FUNCTIONAL TESTS (DOES IT BEHAVE?)
• Purpose: Verify core features work end-to-end:
  - Chat widget interactions (send, receive, error states).
  - Admin flows (upload doc, see it listed, re-index).
  - Basic analytics views.
• When:
  - Before marking a milestone as “done”.
  - Before sharing a staging URL with a client.

LAYER 3 – RAG-SPECIFIC EVALUATION (IS IT USEFUL AND SAFE?)
• Purpose: Test the *quality* of retrieval-augmented answers:
  - Accuracy: Does the answer match the docs?
  - Grounding: Is it based on the retrieved context only?
  - Hallucinations: Does it ever confidently say things that are not true?
• When:
  - At least once at the end of Week 2.
  - Again after any major RAG changes (chunking, embeddings, prompts).

You don’t need an enterprise-grade test framework for this simulation, but you
do want to adopt the **mindset** of structured testing rather than random clicking.

1.2: RAG EVALUATION PLAN (TEST SET, METRICS, AND PROCESS)
---------------------------------------------------------

STEP 1 – BUILD A SMALL TEST SET
• Size: 15–30 questions.
• Source:
  - Take real or realistic FAQs from your chosen tech docs (e.g. React/Next.js docs)
    or from your fictional AcmeDesk docs.
• Types of questions:
  - Direct fact questions.
  - “How do I…?” procedural questions.
  - Clarifications (e.g. “Can I do X on the Starter plan?” if plans exist).

Example (AcmeDesk-style):
• "How do I add a new support agent to my workspace?"
• "Can I connect AcmeDesk to Slack?"
• "What’s the difference between the Pro and Enterprise plans?"
• "How do I export all tickets from last month?"

STEP 2 – DEFINE SIMPLE METRICS
• For each question you log:
  - Answer rating:
    - Correct
    - Partially correct
    - Incorrect
    - Escalate (bot refused and suggested a human)
  - Notes:
    - Which docs it used (if visible).
    - What went wrong (if incorrect).

AGGREGATE METRICS:
• Accuracy (Correct + Acceptable Escalate) / Total.
• Hallucination rate (Incorrect / Total).

TARGETS FOR THIS PORTFOLIO PROJECT:
• Accuracy: ≥ 80% correct or acceptable.
• Hallucination rate: Aim for 0 on sensitive questions (e.g. pricing, policy).

STEP 3 – RUN THE EVALUATION
• Process:
  - Use staging UI.
  - Ask each question once or twice (optionally with small wording variations).
  - Log results in a simple table (Google Sheet or Markdown).
• Outcome:
  - You’ll know:
    - Which kinds of questions the system is strong at.
    - Where retrieval or prompts need improvement.

IN YOUR DOCUMENTATION:
• Include a short section:
  - "RAG Evaluation" with:
    - Test set size.
    - Final metrics.
    - 2–3 bullet notes on limitations and future improvements.

1.3: MANUAL TEST CHECKLIST (WHAT YOU ACTUALLY CLICK THROUGH)
------------------------------------------------------------

Before you call v1 “done”, run through this checklist manually in staging and
production. Treat this like the checklist you’d follow while on a call with a
client during a live demo.

CHAT WIDGET (FRONT-END)
• Loads correctly on:
  - Desktop (at least one major browser).
  - Mobile (simulated via dev tools).
• Behaviors:
  - Open/close actions work.
  - Can type and send messages with Enter and click.
  - Typing indicator appears when waiting for a response.
  - Messages render with correct alignment (user vs bot).
  - Scrolls to latest message automatically.
  - Clear conversation button works.

BACKEND & RAG
• Health checks:
  - `/api/health` returns expected status.
• Basic chat:
  - Sends a generic greeting and receives a response with no errors.
• RAG behavior:
  - Ask 3–5 questions whose answers you know from the docs; verify:
    - Answers mention correct information.
    - If docs don’t contain the answer, bot says it’s unsure or escalates.
• Error handling:
  - Temporarily break your OpenAI key in dev:
    - Check that the error shown to the user is friendly (no stack traces).

ADMIN PANEL
• Login/access:
  - Admin panel is not publicly indexable (e.g. simple auth).
• Documents:
  - Upload a new document and see status change from "Processing" to "Ready".
  - That document’s content is used in subsequent answers.
• Analytics:
  - At least one simple chart or table updates after test conversations.

PERFORMANCE
• Response time:
  - For 5–10 typical queries, responses generally return in < 3 seconds.
• Stability:
  - No obvious memory leaks or repeated crashes in logs under light load
    (even just refreshing and sending many messages).

You can keep this checklist as `TEST-CHECKLIST.md` in the repo.

1.4: OPTIONAL AUTOMATED TESTS (WHERE THEY ADD VALUE)
---------------------------------------------------

You don’t need full test coverage for a portfolio project, but adding a few
high-signal automated tests demonstrates professionalism.

GOOD CANDIDATES:
• Unit tests for:
  - Chunking logic (given text, verify chunks and overlaps).
  - Prompt construction (given query + context, ensure strict instructions).
• API tests for:
  - `/api/health` returns 200.
  - `/api/chat` with a simple mock LLM returns expected JSON shape.

EXAMPLE (PYTHON + PYTEST STYLE DESCRIPTION)
• `tests/test_chunker.py`:
  - `test_chunker_respects_max_tokens()`
  - `test_chunker_preserves_section_boundaries()`
• `tests/test_api_health.py`:
  - `test_health_returns_ok()`

You can leave actual implementation for when you start coding, but having this
testing plan ready makes it easier to start in a structured way.

SECTION 2: REPOSITORY & ENVIRONMENT STRUCTURE
================================================================================

2.1: RECOMMENDED REPO LAYOUT FOR THE CHATBOT PROJECT
----------------------------------------------------

You’ll likely end up with something like:

```
rag-customer-support-chatbot/
  frontend/
    app/              # Next.js app router pages
    components/       # Chat UI, admin UI components
    lib/              # Front-end utilities
    public/           # Static assets (logos, icons)
  backend/
    app/              # FastAPI/Express endpoints
    core/             # RAG logic (ingestion, retrieval, prompts)
    models/           # Pydantic/TypeScript models, schemas
    tests/            # Backend tests
  infra/
    docker/           # Dockerfiles (if used)
    scripts/          # Deployment or helper scripts
  docs/
    architecture.md   # Architecture explanation and diagrams
    admin-guide.md    # How to use the admin panel
    rag-eval.md       # RAG evaluation results and test set summary
  .env.example        # Example env file (no secrets)
  README.md           # Main README for the project
  LICENSE             # Optional, but good practice
```

This structure:
• Separates front-end and back-end clearly.
• Has a dedicated space for documentation.
• Makes it easy for reviewers (or clients) to find what they care about.

2.2: ENVIRONMENT MANAGEMENT (.ENV, SECRETS, AND CONFIG)
-------------------------------------------------------

GOALS:
• Never commit secrets.
• Make it easy for someone else to run the project in their own environment.

FILES:
• `.env` (local, not committed):
  - `OPENAI_API_KEY=...`
  - `VECTOR_DB_URL=...`
  - `DATABASE_URL=...`
• `.env.staging`, `.env.production` (managed in your hosting provider, not
  stored in the repo).
• `.env.example` (committed):
  - Contains the same keys but with placeholder values:
    - `OPENAI_API_KEY=your-openai-key-here`
    - `DATABASE_URL=postgres://user:pass@host:5432/dbname`

IN `README.md`, INCLUDE:
• A short section:
  - "Environment variables"
  - List of variables with one-line explanations.

2.3: SCRIPTS AND TASK RUNNER FOR COMMON COMMANDS
-----------------------------------------------

Having a few standard commands makes your project feel professional and easy to
work with.

EXAMPLES (DESCRIBED, YOU’LL IMPLEMENT LATER):
• `make dev` or `npm run dev-all`:
  - Starts frontend and backend in dev mode.
• `make test` or `npm run test`:
  - Runs backend tests and any front-end tests you add.
• `make ingest`:
  - Runs the ingestion pipeline to index docs into the vector DB.
• `make format`:
  - Runs formatters (Black, Ruff, ESLint, Prettier, etc.).

Even a simple `scripts/` folder with shell/PowerShell scripts is enough. The key
is to have **repeatable commands** rather than manual, ad-hoc steps.

3.2: LIVE DEMO SETUP AND ACCESS STRATEGY
----------------------------------------

GOAL:
• Give potential clients a **zero-friction** way to see the chatbot working.

  - Public chat widget with limited features (safe to show to anyone).
